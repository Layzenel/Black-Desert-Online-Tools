# Чистый код в BDO Tools

Код должен легко читать человек, который видит его впервые. Если для понимания файла нужно
прокручивать экран вверх-вниз и держать в голове пять классов — файл надо разделить.

## Один тип — один файл

- Каждый публичный или `internal` класс, интерфейс, `enum`, `object` и `@Composable`-компонент
  живёт в своём файле. Имя файла совпадает с именем типа: `PortraitsState.kt`, `ModalWindow.kt`.
- В одном файле с типом можно держать только то, что без него не имеет смысла:
  - `private` функции и константы, которые использует только этот тип;
  - перегрузки одной функции (`ActionButton(text)` и `ActionButton { content }`);
  - `sealed`-иерархию, если её наследники — короткие `data class`/`data object` без логики
    (`PortraitsEvent` со всеми событиями).
- Файл с одними top-level функциями называется по теме: `CharacterOrder.kt`, `DecorationFile.kt`.
- Если `private` composable в файле экрана вырос больше ~40 строк или нужен второму экрану —
  выноси его в свой файл как `internal`.

## Размеры

- Файл — до ~200 строк. Больше — ищи, что вынести.
- Функция — до ~30 строк и один уровень абстракции. Длинную функцию разбей на шаги с понятными именами.
- Composable-функция — одна смысловая часть экрана. Окно = заголовок + части, каждая часть — своя функция.
- Не больше 4–5 параметров у обычной функции. Если больше — объедини их в класс состояния.
  У composable-компонентов допустимо больше, если это `modifier`, слоты и колбэки.

## Структура модуля фичи

```
feature/<имя>/src/commonMain/kotlin/.../<пакет>/
├── domain/                 модели и чистая логика, без Compose и без I/O
├── data/                   доступ к файлам и сети; интерфейсы отдельно от реализаций
├── presentation/
│   ├── <Имя>ViewModel.kt   только связывает события, состояние и данные
│   ├── state/              <Имя>State, состояния окон, Notice, Busy …
│   ├── event/              <Имя>Event
│   └── ui/                 Route, Screen и папки частей экрана (grid/, restore/, editor/ …)
└── di/
```

## SOLID

- **S — одна причина для изменения.** ViewModel не рисует пиксели и не кодирует файлы: это делают
  отдельные классы (`PortraitRenderer`, `PortraitDecorator`, `BmpEncoder`). Composable не ходит в данные.
- **O — расширение без правки.** Новый значок — новый `enum`-элемент, SVG и строка; код отрисовки не меняется.
- **L — подстановка.** Реализация интерфейса (`BrowserPortraitsStorage`) ведёт себя так, как описано в
  KDoc интерфейса, и не бросает неописанных исключений.
- **I — маленькие интерфейсы.** Лучше `PortraitsStorage` и `ImageSource`, чем один «файловый менеджер на всё».
- **D — зависимость от абстракций.** ViewModel и репозиторий получают интерфейсы через конструктор (Koin),
  а не создают реализации сами. Тесты подменяют их хранилищем в памяти.

## KISS

- Самое простое решение, которое работает. Не добавляй слой, паттерн или обобщение «на будущее».
- Предпочитай неизменяемые `data class` и `StateFlow.update { it.copy(...) }`.
- Не прячь логику в хитрые однострочники: понятные три строки лучше.

## DRY

- Одинаковый код в двух местах — повод вынести общую функцию или компонент
  (сетка портретов на странице и в окне копий — один `PortraitGrid`).
- Повторяющаяся обработка ошибок, ожидания и прогресса — в одну приватную функцию ViewModel.
- Но не объединяй код, который похож случайно и будет меняться по разным причинам.

## YAGNI

- Не пиши код, параметры и настройки, которые сейчас никто не использует.
- Удаляй мёртвый код: шаблонные файлы, неиспользуемые функции и зависимости. Git всё помнит.
- Исключение — компоненты дизайн-системы в `platform/uikit`: это библиотека, её компоненты
  нужны для будущих страниц и показаны в каталоге `#showcase`.

## Именование и комментарии

- Имена говорят, *что* это и *зачем*: `restoreDialog`, `applyRestore()`, `PortraitWrite`.
  Без сокращений вроде `mgr`, `tmp`, `data2`.
- KDoc у каждого публичного типа и неочевидной функции: что делает и почему так. Не пересказывай код.
- Комментарий внутри функции — только когда без него непонятно *почему*.

## Перед тем как закончить

1. Нет файлов с несколькими публичными типами, кроме разрешённых выше случаев:
   ```bash
   grep -rlcE "^(data |sealed |enum |abstract |internal |private )?(class|interface|object) " --include=*.kt platform shared feature
   ```
   Открой файлы, где совпадений больше одного, и проверь, что это разрешённый случай.
2. Нет файлов длиннее ~200 строк без веской причины:
   ```bash
   find platform shared feature -name "*.kt" -path "*src*" | xargs wc -l | sort -rn | head
   ```
3. Сборка и тесты проходят, приложение открывается в браузере.
