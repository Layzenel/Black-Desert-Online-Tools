# Оверлей поверх игры

Всё поверх игры — только настольная версия (`desktopMain`); на сайте те же `expect` ничего не показывают.
Программа только **читает экран, положение курсора и нажатия** (Raw Input, см. «Клавиши»): никаких хуков ввода
(`SetWindowsHookEx`), перехвата и задержки ввода, чтения памяти игры и нажатий за игрока.

## Где что лежит

Общая основа — `platform/composable`, пакет `composable.overlay`: её видит любая фича (фичи зависят только от
`composable`). Фича добавляет своё поверх игры через **`OverlayContribution`** в своём Koin-модуле
(`single(named("<фича>")) { … }`), корень приложения собирает все вклады (`getAll`) и показывает их в `OverlayHost`.

| Что | Где |
|---|---|
| Контракт фичи | `OverlayContribution(id, windows, tabs, settings)`: `id` — маршрут вкладки программы для «открыть программу» (`OverlayScope.openApp`), `OverlayScope.aside` — показать что-то рядом с меню (схема комбо под курсором), `windows` — окна поверх игры, `tabs` — `OverlayTab(order, title, content)` в общем меню, `settings` — пункты фичи в общей вкладке «Настройки» (её первой собирает `OverlayHost`) |
| Окно поверх игры | `GameOverlayWindow(id, anchor, size)` (`expect`, desktop — `GameOverlayWindow.desktop.kt`); место по `id` в `Preferences` (`OverlayPositions.kt`, узел `bdo-tools/combo-overlay`), до первого перемещения — у `OverlayAnchor`; выросшее окно сдвигается внутрь экрана |
| Размер и непрозрачность | `ScaledOverlay(scalePercent, opacityPercent)`: размер через `LocalDensity` — окно растёт целиком; допустимый размер любого окна — `OverlayScalePercent` (20–100 %) |
| Кнопка и меню | `OverlayHost` → два окна: `OverlayMenuWindow` + `OverlayMenuButton` (значок программы) и `OverlayPanelWindow` + `OverlayMenuPanel` (окно «BDO Tools оверлей», вкладки всех фич по `order`). Меню двигается отдельно от кнопки — за шапку (`GameWindow(titleBarModifier)`), его место — `menuPanel` в `Preferences`; пока меню не двигали, оно открывается под кнопкой (`savedPanelPosition`). То, что вкладка показывает рядом (`aside`), — в своём окне со стороны центра экрана (`AsideWindow`, клики сквозь него): пока оно было в окне меню, окно росло под курсором, наведение терялось, и меню у правого края дёргалось. Перетаскивание обоих окон — `Modifier.windowDrag`. ПКМ по значку — `OverlayActive` (вкл/выкл, не сохраняется между запусками): окна оверлея показываются по `rememberOverlayShown()` (игра впереди и оверлей включён), кнопка — по `rememberGameActive()`. Щиток в значке вместо ромба (`overlay_app_icon_admin`) — игра от администратора (`isGameElevated`: отказ в чтении токена тоже значит «повышен») |
| Игра на переднем плане | `isGameForeground()` (JNA, `BlackDesert64.exe`), в UI — `rememberGameActive()`; сквозные клики — `setClickThrough` (всё — `desktopMain`) |
| Корень в приложении | `shared/src/desktopMain/.../window/DesktopApp.kt`: `OverlayHost` стоит рядом с окном программы, а не внутри него — скрытое в трей окно не перерисовывается. Общая ViewModel — `ViewModelStoreOwner` приложения; подписка на состояние в окнах поверх игры — `collectAsState` (вне окна программы нет `LifecycleOwner`) |
| Помощник комбо | `feature/comboAssist/.../overlay/ComboOverlayContribution.kt`: два окна — трекер (`ComboOverlayContent` по `OverlayStyle`: `Next` — `NextSkillsOverlay`, `Focus` — `FocusOverlay`, у `BottomCenter`) и схема комбо (`SchemaOverlay`, окно `combo-schema` у `CenterLeft`, показ — `OverlaySettings.schemaShown`, ориентация `Combo.vertical` — только у схемы). Всё на подложке `TooltipPanel`, тот же вид — в предпросмотре вкладки «Настройки трекера». Пометка шага (`ComboCell.note`) — под трекером (`StepNote`). Ещё тултипы слотов (`SlotTooltipWindow`, `SlotUnderCursor.kt`) и щиты защиты в правом верхнем углу иконки слота (`SlotShieldsWindow`: защита в PvP по английскому тултипу — `skillProtections`, строки «(PvE only)» пропускаются), вкладка «Комбо» (`OverlayComboTab`) и пункт в «Настройках»; настройки (`OverlaySettings`) — в `combos.json` |
| Чтение экрана (комбо) | `data/history/ScreenSkillHistorySource.kt`: история умений + слоты перезарядок (`data/slots/CooldownSlotWatch`) + клавиши (`data/keys`) + полоска ресурса (`data/resource`); персонаж — `data/slots/PlayedLayout` (журнал игры, запасной — `PlayedCharacterDetector`), видимость каждого слота — `data/slots/slotVisibility` |
| Пинг | `feature/gameInfo`: окно пинга и вкладка «Информация» (`GameInfoOverlay.kt`), настройки — `Preferences` `bdo-tools/game-info` |
| Окно программы и трей | `shared/src/desktopMain/.../window/` (`DesktopApp`, `AppTray`, `CloseChoiceDialog`) |
## Правила окон

- Все окна поверх игры: `undecorated`, `transparent`, `alwaysOnTop`, **`focusable = false`** — клик по ним не уводит игру
  с переднего плана. Видны только пока игра на переднем плане (`rememberGameActive`).
- **Сквозные клики** (`setClickThrough`, `WS_EX_TRANSPARENT`): тултипы, щиты и значки контролей — всегда. Окна
  `GameOverlayWindow` (трекер, схема, пинг) и кнопка меню ловят мышь, пока курсор показан (`rememberCursorShown`,
  `isCursorShown` — `GetCursorInfo`): окна тянутся зажатой ЛКМ (`WindowDraggableArea`), отдельного режима перемещения
  нет. Пока игра прячет курсор (режим боя), клики сквозь них уходят в игру — атака не достаётся оверлею. Тултип слота
  тоже не показывается при спрятанном курсоре, а щиты и значки контролей (`SlotShieldsWindow`), наоборот, видны только
  при спрятанном и на всех слотах: с курсором открыты окна игры, а закрыты ли ими слоты, по экрану надёжно не понять
  (2026-11-26: проверки по иконке и по рамке слота прятали значки при движении и оставляли их под инвентарём).
- **Размер — по содержимому**: `wrapContentSize(unbounded = true)` + `onSizeChanged` → `state.size`. Внутри такого окна
  нельзя `verticalScroll`/`fillMax*` без ограничения (бесконечная высота роняет программу) — поэтому у `ComboOverlay`
  есть `inGame = true`: без прокрутки и без тултипов умений при наведении.
- **Не показывать окно, пока оно не встало на место**: сначала замер и позиция, потом `visible = true` (иначе мелькает
  в левом верхнем углу — см. `SlotTooltipWindow`).
- **Порядок окон**: кнопка меню всегда над оверлеем — оверлей при каждом появлении увеличивает
  `OverlayLayers.overlayShown`, окно кнопки в ответ делает `toFront()` (с паузой, чтобы оверлей успел показаться).
- **Перетаскивание кнопки и меню** (`windowDrag`): свой `pointerInput` с `detectDragGestures` раньше `clickable` (иначе клик съедает нажатие),
  и окно ставится по `MouseInfo` на экране напрямую через `window.setLocation` — сдвиги внутри окна отстают.
  Позиция в состоянии и в `Preferences` (`bdo-tools/combo-overlay`) — когда отпустили.
- Всплывающие списки (`DropdownSelect`, `OptionsMenu`) в маленьких окнах обрезаются — внутри меню оверлея только
  обычные списки (`MenuItem`) и кнопки.
- Координаты: `RelativePosX/Y` элементов игры — доли экрана; Java отдаёт курсор и окна в логических пикселях,
  снимок экрана — в настоящих (`captureScreen` берёт лучший вариант `createMultiResolutionScreenCapture`).

## Чтение экрана

- Слежение за игрой (история, слоты, бафы гнева, ресурс, клавиши) идёт, только пока оверлей комбо показан (настольная
  версия; «Скрыть» в меню оверлея его останавливает, `ComboViewModel.restartWatching`). Видимость слотов
  (`slotVisibility`, 10 снимков в секунду) проверяется отдельно и только пока она нужна: включены тултипы умений
  на слотах или показан трекер (`ComboOverlayWindows` подписывается на `hiddenSlots` лишь тогда, без подписки поток
  стоит). Щитам и контролям она не нужна — они видны при спрятанном курсоре. Пока игра не на переднем плане, программа
  за ней не следит: экран не снимается, файлы слотов не читаются, иконки не качаются (`ScreenSkillHistorySource`).
  20 кадров/с: история умений (≈240×54 px) и полоска ресурса. Новая строка истории — по тексту (`HistoryLines`:
  нижняя строка пустеет при сдвиге) или по смене иконки нижней строки на другое умение два кадра подряд
  (`HistoryIconChange`, в журнале «line found by icon change»): по тексту пропускали строки, которые игра пишет
  (2026-11-26, Страйкер: 3035 «Абсолют: Удар лодыжкой» и 2550 в части проходов).
- Чему верить (`HistoryMerge`): 1) история, 2) слот перезарядки или хотбара (`CooldownSlotWatch` — два ряда `SlotRowWatch`,
  с хотбара — только умения класса (есть в справочниках), которых нет на видимых слотах перезарядки (умения не
  класса, у Страйкера 62863–62865, темнели без применения, 2026-11-26); + `SlotDarkening`; ждёт строку
  истории 600 мс, потом выпускается сам), 3) клавиши с расходом ресурса (`data/keys/KeyStepWatch`). Одно применение
  из разных источников за 1,5 с засчитывается один раз; нажатие умения, которое уже ждёт слот, не учитывается.
  Клавиши слушаются **только для умений из `Combo.keyTracked`** — у них в редакторе снят флаг «Видно в истории или на
  слоте» (`TrainingController.keySteps`). Слоты убирали 2026-11-20 (иконка проявляется неровно, слот срабатывал по
  5–7 раз за перезарядку) и вернули 2026-11-21 по просьбе пользователя — на практике слоты точнее клавиш; повторы
  гасит `SlotDarkening`: сработавший слот следится снова, только когда цветность вернулась к 0,85 прежней.
  Ошибку слота или клавиш поправляет строка истории: умение не по порядку переводит трекер на него
  (`ComboTracker.outOfOrder`).
- Трекер, схема и тултипы прячутся вместе со слотами: `slotVisibility` раз в 100 мс узнаёт
  каждый слот по своей иконке (`SlotVisibility.recognized`) и отдаёт номера скрытых. По своей иконке узнаётся
  меньшинство слотов (2026-11-20: 5 из 20, пара — раз в 0,6 с на перезарядке; требование «узнан каждый» убрало
  тултипы и моргало щитами), поэтому: все скрыты — 4 проверки подряд узнано меньше двух; отдельный слот скрыт — он
  узнаётся стабильно (скользящая доля узнаваний ≥ 0,3; «узнан хоть раз» моргал слотами, узнаваемыми раз в 2 с), а теперь
  15 проверок подряд нет; редко узнаваемый слот видим вместе со всеми. Тултипы рисуются
  только на видимых слотах, трекер и схема прячутся, когда скрыты все.
- Клавиши: Часть продолжений связок с КД 0 игра пишет в историю **не всегда**
  (Серафим: 9708 «Комбо: Сила разрушения» — в одном проходе из пяти; 9855 пишется всегда; замер 2026-11-20 по
  `watch.log`, причина не известна). Нажатие подтверждает только шаг, которого трекер ждёт сейчас или сразу после
  ожидаемого (`TrainingController.keySteps`, `matchKeyStep`); шаг «после X» — только если клавиши X нажали раньше
  (иначе ЛКМ прошлого шага засчитывала продолжение). Нажатие засчитывается сразу: ожидание строки истории
  (0,1–0,75 с) игрок видел как паузу подсказки. Строка истории того же умения за 1,5 с — то же применение; если
  игра сделала другое, трекер поправит её строка. Продолжение, чей запуск ещё не выпущен, ждёт его.
  Запрет «видела история — клавиши не нужны» ломал 9708.

## Гнев Чёрного духа

- У комбо может быть вариант под гневом (`Combo.rage`, правится переключателем над холстом; новому комбо Серафима
  добавляется сразу). Трекер ведёт `ComboState.tracked`: под гневом, пока `rageActive` и вариант есть.
- `data/rage/rageBuffs` (поток `SkillHistorySource.rageActive`, раз в 300 мс, пока слежение идёт и у комбо есть
  вариант): область вокруг «Списка усилений» (`UIData Index="119"`, `RageBuffGeometry`), три эталона
  (`RageBuffMatcher`: все места каждого со счётом < 15) — **три иконки подряд в одном ряду по порядку 1-2-3**
  (`RageBuffSearch.triple`). Тех же иконок мало: они бывают у других бафов (2026-11-20 трекер срабатывал без гнева),
  поэтому начало гнева — тройка с таймером «59 с.» под каждой (`RageTimerReader`: маска белого текста против образца
  `timer59.png`, мера Жаккара ≤ 0,45; свои 0–0,25, «16 м.» 0,66–0,78). С этого момента гнев активен 59 с (`RageClock`),
  что бы ни было на экране; повтор «59 с.» в ту же секунду таймер не продлевает. При смене трекер перезагружается
  с той же перезарядкой (`restartTraining`).
- Под гневом окна трекера и схемы — на `RagePanel` (токены `rage*`, огонь рисуется в `drawBehind`), иначе `TooltipPanel`
  (`OverlayPanel`).

## Клавиши

- `RawInputListener`: скрытое окно `STATIC` + `RegisterRawInputDevices` с `RIDEV_INPUTSINK` (клавиатура и мышь),
  свой поток с циклом сообщений. Это копия ввода, а не хук: игру не задерживает.
- Игра запущена от администратора: ввод её окна Windows отдаёт только процессу с теми же правами или с UIAccess.
  Без них слушатель работает, но нажатий в игре нет. В `watch.log` — `key input: listening` и строки `key …`.
- Клавиши действий — у каждого персонажа свои (`ShortcutKey_Action_Key`, `SlotLayout.keys`), команды — `{KeyBind:…}`
  английского текста навыка (`keyVariants`: строка и «or» — варианты, «+» — зажать вместе).
- **Нажатие — только намерение, не момент шага.** Нажатое рано умение не выходит, а игроки жмут и держат клавиши
  следующего умения заранее, во время анимации предыдущего («предикт», 2026-11-20): засчитывать по нажатию — трекер
  убегает на шаг вперёд. Поэтому шаг умения с заметным расходом (`requiredMp >= 20` у bdolytics →
  `KeyCommand.visibleSpend`) засчитывается, когда умение **началось**: нажатие ждёт до 2,5 с проседания полоски ресурса
  на 3+ px (`data/resource`: `ResourceWatch` → `ResourceBar` → `ResourceDrops`). Каждое проседание (всё в пределах 150 мс —
  одно) забирает одно намерение — самое раннее нажатое до него (`ResourceDrops.claim`), шаг — в момент проседания.
- **Дешёвые умения — по нажатию** (2026-11-20, Страйкер): заливка дрожит на 1–2 px и без расхода (229↔227 на полном
  ресурсе, всплески до 240), а связки по 5 из ~850 — это 1–2 px, и то же умение тут же восполняет ресурс ударами.
  Отличить их расход от шума нельзя, поэтому умения дешевле порога, на SP и без стоимости (и любые, пока полоска не
  найдена) засчитываются сразу по нажатию; ошибку поправит история.
- **Зажатая клавиша — цепочка умений**: пока держат ЛКМ, игра сама применяет умения на неё подряд, а нажатие одно.
  Свежее (≤ 200 мс) проседание, которое не забрало ни одно нажатие, достаётся шагу, которого ждут сейчас, если его
  команда целиком зажата ещё до прошлого шага, засчитанного клавишами, и проседание не раньше 0,25 с после него
  (иначе это расход того же умения или новое нажатие) — `matchHeldStep`, `ResourceDrops.claimFresh`; в журнале —
  «started while … held». Дешёвый шаг на зажатой команде засчитывается, когда она продержалась 0,6 с после прошлого
  шага («held after previous step», `HELD_STEP_MS` — догадка). Одно умение клавишами дважды за 1 с не засчитывается
  (`HistoryMerge.onKey`).
- Команды навыков: часть «Hold X to …» («зажми, чтобы…») — что делать во время умения, а не как его начать
  (`keyVariants`, `PURPOSE`): у 7984 Агента «Hold ПКМ to fire continuously» давала «просто ПКМ», как у 7988 перед ним.
- Полоска ресурса: цвет у классов разный (белый, голубой, зелёный, красный, оранжевый…), поэтому ищется по месту —
  первая полоса под красной полоской HP (`locateResourceBar`, левый край сверяется с нижним рядом HP: без «Разделения HP»
  полоски скошены); заливка — светлые пиксели от левого края до тёмной пустой части (≈50) или рамки, самый длинный ряд
  (цифры и блёстки на заливке её не обрывают). Область поиска — вокруг `UIData Index="13"` или панель слева вверху
  при `Bool Index="72"` = `true`. Проверено на двух скриншотах 2026-11-20 (`ResourceBarPixelsTest`): 452/490 → 211 px
  из ≈222 и 249 px.
- **Раскладку слотов брать только у персонажа, которым играют** (`PlayedLayout`): сначала по журналу игры
  (`CharacterJournal`, новейший `Cache\11\MyJournal\<CharacterNo>_*.bcf` в папке установки — она берётся из пути процесса
  игры, `foregroundGameFolder`), иначе по слотам на экране (`PlayedCharacterDetector`). Не «новейший файл персонажа»:
  его игра пишет, когда с персонажа уходят. У двух персонажей одного класса слоты бывают разложены по-разному (так
  «шаг 3» читался как «5.2»). Персонаж из журнала известен и со скрытыми слотами — тогда слотов в раскладке нет:
  ни тултипов, ни щитов, а комбо игрок выбирает сам (`followPlayedCharacter` переключает комбо только при смене класса).
  `CooldownSlotWatch` перечитывает файлы персонажей, когда меняется журнал (`CharacterJournal.stamp`, в `watch.log` —
  «game journal changed»); `playedSlots` (тултипы и значки) читает их заново при каждой проверке раз в 5 с.
- Всё, что видно в слежении, пишется в `Документы\Black Desert\BDO Tools\comboAssist\watch.log` — сначала смотри его.
  Нераспознанная строка: в журнале лучший кандидат со счётом и отрывом, рядом картинка иконки `miss-<мс>.png`.
  Пороги совпадения — `accepts` в `IconMatch.kt` (иконка в истории бывает темнее справочной).


## Пинг игры

- `feature/gameInfo/.../data/DesktopGamePingSource` раз в секунду находит процесс `BlackDesert64.exe` по снимку списка процессов
  (`CreateToolhelp32Snapshot`: путь процесса, запущенного от администратора, Java не видит) и его TCP-подключения
  (`GetExtendedTcpTable`, `TcpTable.kt`). Сервер — подключение к порту 8889, иначе любое не веб-подключение;
  ищется заново при каждой проверке: адрес меняется при смене канала и переподключении.
- Задержка — `SmoothedRtt` из `GetPerTcpConnectionEStats` (как «Монитор ресурсов»). Читать её можно без прав, а
  включить сбор — только администратору (`SetPerTcpConnectionEStats` → 5, нет доступа). Программа включает сбор
  для каждого нового подключения сама (после загрузочного экрана игра подключается заново); без прав —
  `PingReading(needsAdmin = true)`, «— мс» и подсказка во вкладке «Информация».
- Не мерить время установки своего TCP-соединения: VPN и ускорители (у игрока туннель `tun0`, локальный адрес
  `172.19.0.1`) отвечают на него сами — выходит 1 мс. ICMP-пинг сервер режет.
- Фича `feature/gameInfo`. Замер идёт, только пока пинг показывают (`GameInfoViewModel`); окно — `GameOverlayWindow` с id `ping`.

## FPS игры

- Время ПК — в конце той же строки (`TimeValue`, `pcTime` — `expect`: на Desktop `java.time`), включатель «Показывать время», флаг `timeShown` — девятое поле строки настроек пинга.
- Справа от пинга в том же окне (`PingBadge`), включатель «Отображать FPS» во вкладке «Информация», флаг `fpsShown` —
  четвёртое поле строки настроек пинга, вид `FpsStyle` («Компактно» / «Подробно») — пятое.
- `PresentTrace` держит моменты кадров за 5 с, `FrameStats.of` (domain) считает по ним FPS за последнюю секунду,
  «1% low», худший кадр и фризы (кадр дольше 2 средних); подробный вид рисует `FrameGraph`. Панель — `Column` с
  `width(IntrinsicSize.Max)`: график растягивается по строке, а не на бесконечную ширину окна по содержимому.
- `data/PresentTrace` (JNA, `advapi32`): своя ETW-сессия реального времени `BDO Tools FPS` с провайдером
  `Microsoft-Windows-DxgKrnl` (`{802EC45A-1E99-4B83-9920-87C98277BA9D}`, ключевое слово `0x8000000`), событие 184
  `Present_Info` — по одному на кадр. Не `Microsoft-Windows-DXGI`: в Windows 26300 у него другие номера событий, события 42
  `Present_Start` нет совсем (проверено трассировкой `logman` + `tracerpt`, 2026-11-21). Считаются события процесса игры за последнюю секунду по их времени; нет кадров 3 с — «— FPS».
  `FlushTimer = 1` с: иначе редкие события ждут заполнения буфера.
- Запустить сессию может только администратор (`isRunningAsAdmin` из `composable.overlay`): без прав включатель
  недоступен и объяснён. Внешний PresentMon.exe не нужен. Сессия, оставшаяся после аварийного выхода, останавливается
  при следующем запуске (`ERROR_ALREADY_EXISTS`).
- Ноябрь 2026: на машине пользователя события о кадрах одно время не приходили никому (ни PresentMon, ни Game Bar —
  «запустите новую игру»). Если FPS пустой, сначала проверь FPS в Game Bar (Win+G).

## Перед тем как закончить

- Собери обе платформы (сайт должен собираться, хоть окон там и нет) и прогони `:feature:comboAssist:desktopTest`.
- Если программа запущена — закрой её перед пересборкой: перезапись файлов под работающим окном роняет его
  (`ZipException: invalid LOC header`).
- Новые знания о том, как игра рисует свои элементы, — в скилл `game-files`.
